# **5. Functional Requirements — Flow หลัก**

## **FR-01  หน้าช็อปปิ้งใบประกาศ**

Admin เห็นใบประกาศจาก SRC-1 ถึง SRC-5 ในหน้าจอเดียว พร้อมตัวกรองและการเลือกทีละหลายรายการ

•   รองรับการเลือกหลายรายการพร้อมกัน แล้วสั่ง action ทีเดียว

## **FR-02  ดึงเข้า Section ทรัพย์ดีทรัพย์เด็ด**

Admin สั่ง “ดึงเข้าทรัพย์ดีทรัพย์เด็ด” ได้ โดยเป็น action ที่ทำได้ด้วยตัวเองโดยไม่ต้องโคลน [สมมติฐาน — รอยืนยัน Q-04]

## **FR-03  โคลนนิ่งใบประกาศ**

•   โคลน 1 ใบ ระบบสร้างใบโคลนใหม่ ผูกกับ contract ของ Profile นายหน้าบ้านพร้อมจังหวัดปลายทาง

•   ระบบต้องเก็บ cloned_from_post_id เพื่อใช้ซิงก์สถานะ กันโคลนซ้ำ และตรวจสอบย้อนหลัง

•   ต้องบันทึก Audit log: ใครโคลน เมื่อไหร่ จากใบไหน ไปยัง Profile ใด

## **FR-04  กฎการแสดงผลหลังโคลน**

ใบโคลนแสดง 2 จุดเสมอ คือ Section ทรัพย์ดีทรัพย์เด็ด และพอร์ตของ Profile นายหน้าบ้านพร้อมรายจังหวัด ส่วนใบต้นทางจะแสดงหรือไม่ ขึ้นกับประเภทเจ้าของ ตามตารางหัวข้อ 6

# **7. Profile นายหน้าบ้านพร้อมรายจังหวัด**

| ขอบเขตการสะท้อน | สะท้อนทุกใบโคลน หรือเฉพาะใบที่สร้างหลังการแก้ไข |
| ผู้มีสิทธิ์แก้ไข | Admin เท่านั้น หรือมี role อื่นแก้ได้ด้วย |
| ข้อมูลติดต่อ | ใบโคลนแสดงเบอร์ของ Profile รายจังหวัด หรือเบอร์กลางของบ้านพร้อม |
| Audit   | เก็บประวัติการแก้ Profile หรือไม่ (ใคร / เมื่อไหร่ / แก้อะไร) |

# **8. OBJ-1 — Logic การแสดงซ้ำ / Retargeting (“การหลอกหลอน”)**

**สถานะ**  ทั้งหัวข้อนี้เป็น [ข้อเสนอ] ของ BA — requirement ต้นทางมีเพียงชื่อหัวข้อ ใช้เป็นตั้งต้นสำหรับถกกันเท่านั้น ยังไม่ใช่สเปกที่ยืนยันแล้ว

## **8.1 นิยามที่ต้องยืนยันก่อน (Q-16)**

“การหลอกหลอน” หมายถึงข้อใด

|     | **ทางเลือก** | **ความหมาย** |
|-----|----------|----------|
| ก   | Retargeting รายทรัพย์ | ทรัพย์ที่ผู้ใช้เคยกดดู กลับมาโผล่ใน Section ทรัพย์ดีทรัพย์เด็ดในหน้าอื่นหรือวันหลัง |
| ข   | Retargeting รายหมวด | แสดงทรัพย์ที่คล้ายกัน (หมวด / จังหวัด / ช่วงราคาเดียวกัน) ไม่ใช่ใบเดิม |
| ค   | การแสดงซ้ำเชิงความถี่ | ทรัพย์ที่ Admin คัดไว้ถูกยิงซ้ำหลายหน้าเพื่อดันการมองเห็น ไม่ผูกกับพฤติกรรมผู้ใช้ |

## **8.2 โครงกติกาที่เสนอ (สมมติเลือก ก + ข)**

| **องค์ประกอบ** | **ข้อเสนอ** |
|------------|---------|
| สัญญาณที่เก็บ | viewed_post_id · หมวดทรัพย์ · จังหวัด/อำเภอ · ช่วงราคา · timestamp |
| หน้าต่างเวลา | ย้อนหลัง 30 วัน โดยน้ำหนักลดลงตามเวลา (decay) |
| ลำดับการเลือก | ทรัพย์ที่เคยดู → ทรัพย์คล้ายในหมวด/พื้นที่เดียวกัน → ทรัพย์คัดสรรทั่วไป (fallback) |
| Frequency cap | ทรัพย์ 1 ใบ แสดงซ้ำต่อผู้ใช้ไม่เกิน N ครั้งต่อวัน (เสนอ N = 3) |
| เงื่อนไขตัดออกอัตโนมัติ | ผู้ใช้กดปิด · ทรัพย์ขาย/ปล่อยเช่าแล้ว · ผู้ใช้ส่ง lead ของทรัพย์นั้นแล้ว |
| ผู้ใช้ที่ไม่ล็อกอิน | ใช้ session หรือ cookie และต้องมี consent banner |
| Fallback   | ไม่มีประวัติ → แสดงตามจังหวัดที่กำลังดู → ทรัพย์คัดสรรทั่วไป |

## **8.3 ความสัมพันธ์กับสูตร Ranking ที่ทีมทำอยู่**

Section นี้ควรใช้กลไกเดียวกับ Relevance⁺ (Category Boost + Location Boost) และ Pacing ที่ทีมออกแบบไว้ในสูตร ranking แทนที่จะสร้าง logic แยก มิฉะนั้นจะเกิดระบบจัดลำดับ 2 ชุดที่ขัดกันเองบนหน้าเดียวกัน — รอยืนยัน (Q-18)

## **8.4 PDPA**

การเก็บพฤติกรรมการดูรายบุคคลเพื่อแสดงซ้ำ ต้องมีฐานการประมวลผลตาม PDPA (consent หรือ legitimate interest) มีช่องทาง opt-out และมีนโยบายอายุข้อมูล — รอยืนยัน (Q-21)

# **9. OBJ-2 — การเชื่อมกับกระดาน Lead**

## **9.1 Attribution — Lead ตกเป็นของใคร**

เมื่อผู้ใช้ส่งข้อมูลติดต่อจากใบโคลน lead นั้นเป็นของใคร

•   Profile นายหน้าบ้านพร้อมจังหวัดปลายทาง (เจ้าของใบโคลน)

•   เจ้าของใบต้นทาง

•   ทั้งคู่ (แจ้งเตือนคู่ขนาน)

กรณี cobroke ยิ่งซับซ้อน เพราะเกี่ยวข้องกับส่วนแบ่งค่าคอมมิชชัน — รอยืนยัน (Q-07 และ Q-20)

## **9.2 ข้อมูลที่ต้องส่งเข้ากระดาน Lead**

| **ฟิลด์** | **เหตุผลที่ต้องมี** |
|-------|-----------------|
| post_id (ใบโคลน) + cloned_from_post_id | แยกได้ว่า lead มาจากใบโคลนหรือใบต้นทาง |
| source_section = treasure_pick | วัดผล Section นี้แยกจาก channel อื่น |
| is_retargeted (bool) | วัดว่า logic หลอกหลอนสร้าง lead ได้จริงหรือไม่ |
| province_id · contract_id · owner_profile_id | ใช้ route lead เข้าจังหวัดและคู่สัญญาที่ถูกต้อง |

## **9.3 Dedup**

Lead เบอร์เดียวกันที่มาจากใบโคลนและใบต้นทางของทรัพย์เดียวกัน ต้องนับเป็น lead เดียวหรือสองรายการ ต้องกำหนด dedup key ให้ตรงกับกติกาของกระดาน lead ที่มีอยู่แล้ว — รอยืนยัน (Q-19)

## **9.4 ตัวชี้วัดที่ควรมีตั้งแต่วันแรก**

•   Impression / Click / CTR ของ Section ทรัพย์ดีทรัพย์เด็ด

•   จำนวน Lead ต่อใบโคลน

•   CTR เปรียบเทียบระหว่างใบโคลนกับใบต้นทาง

•   สัดส่วน Lead ที่มาจาก Retargeting

•   จำนวนใบโคลนที่ active ต่อจังหวัด

# **11. Acceptance Criteria**

*เขียนในรูปแบบ Given / When / Then สำหรับ QA ใช้เป็นฐานเขียน test case โดยตรง*

**AC-01  โคลนใบประกาศของนายหน้า**

**Given**  ใบประกาศมือสอง สถานะออนไลน์ เจ้าของเป็นนายหน้า

**When**   Admin สั่งโคลนโดยเลือก Profile นายหน้าบ้านพร้อมจังหวัดขอนแก่น

**Then**   ใบโคลนถูกสร้างและผูกกับ contract ของ Profile นั้น และปรากฏใน Section ทรัพย์ดีทรัพย์เด็ด และปรากฏในพอร์ตของ Profile นั้น และใบต้นทางยังแสดงในหน้าเสิร์ชตามเดิม

**AC-02  โคลนใบประกาศที่ไม่ใช่ของนายหน้า**

**Given**  ใบประกาศเช่า สถานะออนไลน์ เจ้าของไม่ใช่นายหน้า

**When**   Admin สั่งโคลน

**Then**   ใบโคลนปรากฏใน Section และในพอร์ต Profile และใบต้นทางไม่ปรากฏในผลค้นหาอีกต่อไป

**AC-03  ทรัพย์รีเฟอร์ (สัญญาปิด)**

**Given**  ทรัพย์รีเฟอร์สัญญาปิดจากบ้านพร้อม ประเภทมือสอง สัญญายังไม่หมดอายุ

**When**   Admin เปิดหน้าช็อปปิ้ง

**Then**   ทรัพย์ดังกล่าวปรากฏในรายการที่เลือกได้ และดึงเข้า Section หรือโคลนได้ตามกติกาเดียวกับ AC-01 และ AC-02

**AC-04  Cobroke — โคลนได้ทั้งเปิดและปิด**

**Given**  ใบประกาศมือสองที่ตั้งค่า cobroke = เปิด และอีกใบที่ตั้งค่า cobroke = ปิด

**When**   Admin สั่งโคลนทั้งสองใบ

**Then**   ระบบสร้างใบโคลนได้ทั้งสองใบ โดยสถานะ cobroke ไม่เป็นเงื่อนไขขัดขวางการโคลน

**AC-05  แก้ไข Profile นายหน้าบ้านพร้อม  [รอยืนยัน Q-17]**

**Given**  Profile นายหน้าบ้านพร้อมจังหวัดชลบุรีมีใบโคลนผูกอยู่ 20 ใบ

**When**   Admin แก้ไขชื่อและเบอร์ติดต่อของ Profile

**Then**   ใบโคลนทั้ง 20 ใบแสดงข้อมูลใหม่ทันทีในทุกจุดแสดงผล

**AC-06  ดึงเข้า Section โดยไม่โคลน**

**Given**  ใบประกาศที่ผ่านเงื่อนไข Eligibility

**When**   Admin สั่ง “ดึงเข้าทรัพย์ดีทรัพย์เด็ด” อย่างเดียว

**Then**   ใบประกาศปรากฏใน Section โดยไม่สร้างใบโคลนและไม่ซ่อนใบต้นทาง

**AC-07  กันโคลนซ้ำ  [รอยืนยัน Q-08]**

**Given**  ใบประกาศที่มีใบโคลนอยู่แล้ว

**When**   Admin สั่งโคลนอีกครั้ง

**Then**   ระบบแจ้งเตือนว่าใบประกาศนี้ถูกโคลนแล้ว และไม่สร้างใบโคลนซ้ำ

**AC-08  ยกเลิกการโคลน  [รอยืนยัน Q-09]**

**Given**  ใบโคลนที่มีอยู่ และใบต้นทางถูกซ่อน (เคส B)

**When**   Admin ลบหรือยกเลิกใบโคลน

**Then**   ใบโคลนหายจาก Section และพอร์ต และใบต้นทางกลับมาแสดงในหน้าเสิร์ชตามสถานะเดิม

**AC-09  Lead จากใบโคลนเข้ากระดาน Lead  [ผู้รับผิดชอบรอยืนยัน Q-07]**

**Given**  ผู้ใช้เปิดใบโคลนจาก Section ทรัพย์ดีทรัพย์เด็ด

**When**   ผู้ใช้ส่งข้อมูลติดต่อ

**Then**   Lead เข้ากระดาน Lead พร้อมระบุ post_id ของใบโคลน, cloned_from_post_id, source_section = treasure_pick และถูก route ไปยังผู้รับผิดชอบที่ถูกต้อง

# **13. สิ่งที่ต้องทำต่อ**

1\. เคลียร์คำถาม Critical 10 ข้อในหัวข้อ 12.1 โดยเฉพาะ Q-16 และ Q-17 ที่ทำให้ requirement 2 ข้อเขียนต่อไม่ได้เลย

2\. เติม Display Matrix (หัวข้อ 6) ให้ครบทุกช่องที่ยังเป็น “รอยืนยัน”

3\. เขียน State Machine ของใบโคลน: สร้าง → แสดง → ซิงก์/แช่แข็ง → ยกเลิก → ลบ พร้อมผลกระทบต่อใบต้นทางในแต่ละสถานะ

4\. ทำ Permission Matrix: Role × Action (ช็อปปิ้ง / ดึงเข้า Section / โคลน / ยกเลิกโคลน / แก้ Profile / ดูรายงาน)

5\. เขียนสเปก Logic หลอกหลอนเป็นเอกสารย่อยหลังได้คำตอบ Q-16 (สัญญาณ · หน้าต่างเวลา · frequency cap · fallback · opt-out)

6\. เขียน Flow การส่ง Lead เข้ากระดาน Lead พร้อม field mapping และกติกา dedup

7\. ระบุ Empty / Loading / Error state ของหน้าช็อปปิ้ง และเคสโคลนไม่สำเร็จ

8\. ทำ Wireframe หน้าช็อปปิ้ง (ตัวกรอง · การเลือกหลายรายการ · ปุ่ม action · modal ยืนยัน)
