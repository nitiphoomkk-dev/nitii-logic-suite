**เป้าหมาย:** ให้ Insert Card ของจังหวัดปัจจุบัน รวมหมวดน่าอยู่ มีโอกาสได้รับตำแหน่งจากการ Shuffle รายการต้นทาง แล้วเลือก Slot A หรือ Slot B ด้วยน้ำหนักจากผล A/B ของภาษาเว็บไซต์นั้น ก่อนแสดงสื่อตามเงื่อนไขภาษา ใช้จำนวนและตำแหน่ง Insert ตามผังของหน้า ไม่เพิ่มการ์ดจากจำนวนภาษาและจำนวนทางเลือก

**คำตัดสินผู้ใช้ล่าสุด:** “ขอแก้คำใหม่เป็น เวทน้ำหนักจาก slot A และ slot B ส่วนภาษาการแสดงผลให้ตรงกับเงื่อนไขภาษา” ใช้แทนข้อความก่อนหน้าที่ให้ Shuffle ทางเลือกภายในหรือจำกัดน้ำหนักเฉพาะภาพ กฎล่าสุดครอบคลุมคู่ A/B ที่เป็นคนละรูปแบบ รวมคู่ Free Text กับ Video ด้วย

**ลำดับการทำงาน:** คัดรายการต้นทางของจังหวัดที่ผ่านเงื่อนไข → Shuffle รายการต้นทางทั้งหมด → เลือกไม่เกินความจุหน้า → ใช้น้ำหนักของภาษาเว็บไซต์เลือก A/B ภายในแต่ละรายการ → ใช้สื่อภาษาที่เลือกหรือไทยสำรองของทางเลือกที่ได้รับเลือก → แสดงรายการต้นทางละหนึ่งการ์ด

**สถานะหลักฐาน:** กฎภาษาและไฟล์ร่วมอุปกรณ์อ้างอิง Insert Card 3 ภาษา; สูตรและวงจรน้ำหนักประยุกต์จาก Top Banner แบบที่ 2 ตามโจทย์รอบนี้ ส่วนการใช้ `web_language` เป็น bucket และการรีเซ็ตตามสื่อร่วมเป็น **กฎประยุกต์ใน Solution** เพื่อให้เลือก A/B ก่อน resolve สื่อได้ ไม่ใช่ข้อความที่ยืนยันไว้แล้วในต้นทาง Top Banner และไม่ใช่หลักฐานว่าระบบจริงทำงานตามนี้ ทั้งข้อกำหนดในร่างนี้มี Priority: Must ภายในขอบเขตงาน เว้นแต่ระบุเป็นข้อเสนอหรือรอคำตัดสิน

## EP-04 Shuffle รายการต้นทางและเวทน้ำหนัก Slot A/B

### 4.1 เลือกรายการต้นทางและตำแหน่ง

| รหัส | เงื่อนไข / การกระทำ | Logic การทำงาน |

| IC2-S01 | เตรียม Candidate ของจังหวัด | แต่ละ Source เข้า Shuffle เพียงครั้งเดียว แม้มี A/B และภาพครบสามภาษา รวมหมวดน่าอยู่ที่ผ่านเงื่อนไขไว้ในชุดเดียว |

| IC2-S04 | Source ใช้ไทยสำรอง  | ยังคงสิทธิ์ Shuffle ตามเงื่อนไขเดิม ไม่จัดไว้ท้ายหรือเพิ่ม/ลดน้ำหนัก Source เพราะจำนวนภาษา |

### 4.2 เลือก A/B ภายใน Source ที่ได้ตำแหน่ง


1. ใช้ภาษาที่ผู้ใช้เลือกเป็น bucket L ของ Source นั้น เช่น เว็บจีนใช้ L=ZH และ P[ZH] ของ Source เดิม
2. ถ้า A และ B พร้อมแสดงทั้งคู่ ให้เวทน้ำหนักจาก Slot A และ Slot B โดยใช้ P_A[L] และ P_B[L] ล่าสุด ไม่ใช้ uniform Shuffle ภายใน
3. ถ้าพร้อมแสดงเพียง A หรือเพียง B ใช้ฝั่งนั้น 100% ช่วง 30–70% ใช้เมื่อมีทางเลือกพร้อมทั้งคู่ ไม่สร้างการ์ดว่างตามน้ำหนักฝั่งที่ใช้ไม่ได้
4. ถ้าไม่มีทางเลือกพร้อมแสดง Source นั้นไม่เข้า Candidate
5. เมื่อเลือก A/B แล้วจึงใช้ EP-03 เลือกสื่อของทางเลือกนั้น ไม่เปลี่ยน bucket หรือลองสุ่มใหม่เพราะได้ไทยสำรอง

น้ำหนักเป็นโอกาสเลือก A/B ไม่ใช้เรียงลำดับ Source ไม่เพิ่มจำนวนการ์ด และไม่รับประกันว่าเปิดจำนวนครั้งน้อย ๆ แล้วต้องได้สัดส่วนตรงตัวเลข หาก CTR สูงอยู่ฝั่ง B ฝั่ง B ได้เป็นฝั่งน้ำหนักสูงได้

## EP-10 สูตร CTR และน้ำหนัก A/B แยกภาษาเว็บไซต์ — แบบที่ 2

**หนึ่ง Source มีสามชุดน้ำหนัก:** ไทย จีน และอังกฤษตาม `web_language` แต่ละชุดรวม Click/Impression ของ PC/Mobile ในภาษาเว็บเดียวกันก่อนหาร ไม่รวมข้าม Source ไม่รวมข้ามภาษาเว็บเพื่อเลือก A/B และไม่เอา `media_language` จาก fallback มาเปลี่ยน bucket

การเลือก bucket ก่อน A/B และนโยบายรีเซ็ตใน EP-12 เป็นกฎประยุกต์สำหรับ Insert ที่มีคนละรูปแบบและไฟล์ร่วม ส่วนสูตร 30–70%, รอบรายวัน เริ่ม 50:50 และเก็บ Performance อ้างอิงแบบคำนวณต้นแบบ ไม่คัดกฎ Top ที่เลือกภาษาภาพจริงก่อน A/B มาปะปน

### 10.1 ขอบเขตข้อมูลและรอบคำนวณ

| รหัส | เรื่อง | Logic การทำงาน |
|------|--------|----------------|
| IC2-CTR01 | หน่วยคำนวณ | Source + `web_language` หนึ่งชุด เปรียบเทียบ A กับ B ใช้กับทั้ง PC/Mobile |
| IC2-CTR02 | รวมอุปกรณ์ | รวม Click ของ A จากทุกอุปกรณ์ใน bucket เดียวกัน และรวม IMP ในขอบเขตเดียวกันก่อนหาร ทำแบบเดียวกับ B ไม่เฉลี่ย CTR ย่อย |
| IC2-CTR03 | ช่วงข้อมูล | ใช้ input สะสมตั้งแต่รีเซ็ตล่าสุดของ bucket นั้น ไม่ล้างเมื่อเปลี่ยนวัน และไม่จำกัดเฉพาะข้อมูลวันก่อนหน้า |
| IC2-CTR04 | รอบรายวัน | คำนวณหลัง 00:00 น. ทุกวัน เวลา Asia/Bangkok ใช้ค่าน้ำหนักใหม่ตอนเลือก A/B ครั้งถัดไป ไม่คำนวณใหม่ทุก Refresh |
| IC2-CTR05 | เริ่มใหม่/รอรายวัน | bucket เพิ่งเริ่ม หรือถูกรีเซ็ตจากการแก้สื่อ ใช้ 50:50 ทันทีจนถึงรอบรายวันถัดไป bucket อื่นคงน้ำหนักเดิม |
| IC2-CTR06 | ข้อมูลคำนวณไม่ได้ | ถ้า IMP รวมของ A หรือ B ใน bucket เป็น 0 หรือ CTR A + CTR B เป็น 0 ให้ bucket นั้น 50:50 ไม่หารศูนย์ ไม่ยืมภาษาอื่น |
| IC2-CTR07 | ข้อมูลอุปกรณ์เดียว | ถ้ามีเพียง PC หรือ Mobile แต่ยอดรวมของทั้ง A/B ใน bucket คำนวณได้ ใช้ข้อมูลนั้นได้ ไม่ต้องรอสองอุปกรณ์ |
| IC2-CTR08 | ภาษาสำรอง | เว็บ ZH แสดง Video TH หรือภาพ TH สำรอง → บันทึก input ใน bucket ZH เพียงครั้งเดียว พร้อม `media_language=TH` สำหรับรายงาน ไม่ลง input TH ซ้ำ |
| IC2-CTR09 | ทางเลือกเดียว | A หรือ B พร้อมเพียงฝั่งเดียว ใช้ 100% ของฝั่งนั้น การมีน้ำหนัก 50:50 หรือ 30:70 ไม่ทำให้เลือกฝั่งที่ไม่พร้อม |
| IC2-CTR10 | แยกจาก Performance | เก็บสถิติจริงและประวัติสื่อไว้หลังเปลี่ยนสื่อ ข้อมูลก่อนรีเซ็ตไม่ย้อนมาเป็น input ใหม่ของ bucket ที่รีเซ็ต |

### 10.2 ตัวแปรและสูตร

กำหนด L = TH, ZH หรือ EN ตามภาษาเว็บ คำนวณแยก Source และ L ทีละชุด

| ตัวแปร | ความหมาย |
|--------|----------|
| IMP_AB_A[L] / CLICK_AB_A[L] | ผลรวม Impression / Click ของ A ใน bucket ภาษาเว็บ L จากอุปกรณ์ทั้งหมดตั้งแต่จุดรีเซ็ตล่าสุดของ bucket |
| IMP_AB_B[L] / CLICK_AB_B[L] | ผลรวมแบบเดียวกันสำหรับ B |
| CTR_AB_A[L] / CTR_AB_B[L] | Click รวม ÷ IMP รวม ของฝั่งนั้นใน bucket L |
| RAW_P_A[L] | สัดส่วนน้ำหนัก A จาก CTR ก่อนจำกัดช่วง |
| P_A[L] / P_B[L] | น้ำหนักเลือก A/B สำหรับ Source และภาษาเว็บ L เมื่อพร้อมทั้งคู่ |

ใช้สูตรเมื่อ IMP ของทั้ง A และ B ใน bucket มากกว่า 0 และผลรวม CTR มากกว่า 0

```text
CTR_AB_A[L] = CLICK_AB_A[L] / IMP_AB_A[L] × 100
CTR_AB_B[L] = CLICK_AB_B[L] / IMP_AB_B[L] × 100
RAW_P_A[L] = CTR_AB_A[L] / (CTR_AB_A[L] + CTR_AB_B[L]) × 100
P_A[L] = MAX(30, MIN(70, RAW_P_A[L]))
P_B[L] = 100 - P_A[L]
```

ถ้าคำนวณไม่ได้ตาม IC2-CTR06 ให้ P_A[L]=50 และ P_B[L]=50 คำนวณจากค่าจริงก่อนปัดทศนิยมแสดงผล ไม่เพิ่มเกณฑ์ IMP/Click ขั้นต่ำในงานนี้

| CTR A | CTR B | น้ำหนักดิบ A:B | น้ำหนักใช้จริง A:B |
|------:|------:|---------------:|-------------------:|
| 3%    | 2%    | 60:40          | 60:40              |
| 9%    | 1%    | 90:10          | 70:30              |
| 1%    | 9%    | 10:90          | 30:70              |
| 2%    | 2%    | 50:50          | 50:50              |
| 0% โดยมี IMP | 2%    | 0:100          | 30:70              |
| 2%    | 0% โดยมี IMP | 100:0          | 70:30              |
| 0%    | 0%    | หารด้วยศูนย์ไม่ได้ | 50:50              |
| ฝั่งใดมี IMP รวม=0 | —     | CTR ไม่ครบสองฝั่ง | 50:50              |

70:30 เป็นกรอบแต่ละฝั่ง ไม่ใช่ค่าคงที่รายวัน และไม่หมายถึงให้ฝั่งที่ชนะได้แสดง 100% หาก A มี Click=0 แต่ยังมี IMP และ B มี CTR มากกว่า 0 ต้องคำนวณแล้วจำกัดเป็น 30:70 ไม่ตีความเป็นกรณีคำนวณไม่ได้

## EP-11 จำลองคำนวณน้ำหนักและเลือกสื่อ

ตัวเลขเป็นข้อมูลทดสอบสมมติของ Source เดียว ไม่ใช่สถิติระบบจริง ทั้งสองอุปกรณ์รวมอยู่ในยอดแต่ละ bucket แล้ว ไม่มีหกคู่ไฟล์ภาษา–อุปกรณ์

### 11.1 คำนวณแยกภาษาเว็บ

| bucket ภาษาเว็บ | A Click / IMP | CTR A | B Click / IMP | CTR B | น้ำหนักดิบ A:B | น้ำหนักใช้จริง A:B |
|-----------------|--------------:|------:|--------------:|------:|---------------:|-------------------:|
| TH              | 400 / 10,000  | 4%    | 200 / 10,000  | 2%    | 66\.6667:33.3333 | 66\.67:33.33       |
| ZH              | 10 / 1,000    | 1%    | 50 / 1,000    | 5%    | 16\.6667:83.3333 | 30:70              |
| EN              | 30 / 1,000    | 3%    | 30 / 1,000    | 3%    | 50:50          | 50:50              |

ตัวอย่าง ZH: RAW_P_A = 1 ÷ (1+5) × 100 = 16.6667 → จำกัดขั้นต่ำ A เป็น 30 → B=70

**เปรียบเทียบเพื่ออธิบายแบบ:** ถ้ารวมข้ามภาษา จะได้ A=440/12,000, B=280/12,000 → CTR ประมาณ 3.6667%/2.3333% → น้ำหนัก 61.11:38.89 ซึ่งเป็นตัวอย่างแบบที่ 1 ไม่ใช่น้ำหนักที่ใช้เลือกในแบบที่ 2 การรวมยอดเพื่อรายงานภาพรวมได้ไม่ทำให้แทน P[TH], P[ZH], P[EN] ด้วยน้ำหนักรวม

### 11.2 น้ำหนักก่อน resolve สื่อ

## EP-12 แก้สื่อและรีเซ็ตเฉพาะ bucket ภาษาเว็บที่กระทบ

**กฎประยุกต์ IC2-D02:** Insert ใช้ไฟล์ร่วม PC/Mobile จึงไม่มีคู่รีเซ็ต TH-PC, TH-Mobile ฯลฯ ให้หาว่า bucket ภาษาเว็บใดใช้สื่อที่เปลี่ยน ทั้งแบบภาษาตรงและไทยสำรอง แล้วเริ่ม input **A และ B ทั้งคู่** ของแต่ละ bucket ที่กระทบใหม่ ตั้งน้ำหนักของ bucket เหล่านั้น 50:50 ทันทีจนรอบรายวันถัดไป input และน้ำหนักของ bucket ที่ไม่กระทบคงเดิม Performance จริงและประวัติเดิมยังอยู่

การพิจารณาผลกระทบต้องครอบคลุมการอ้างสื่อและ eligibility ก่อนและหลังแก้ของ **ทุกทางเลือกที่อาจได้รับเลือก** ไม่ดูเฉพาะผล render ครั้งล่าสุด เช่น เพิ่ม/ลบ EN ที่เปลี่ยนเส้นทางระหว่าง EN ตรงกับ TH สำรองย่อมกระทบ EN ส่วนการลบ TH ที่บังคับของ A อาจทำให้ A ไม่พร้อมทั้งสามเว็บ แม้ยังมี EN/ZH ตรง จึงอาจกระทบทั้งสาม bucket ให้ใช้ขอบเขต bucket ที่เกี่ยวข้องทั้งหมด ไม่เลือก bucket จากชื่อไฟล์อย่างเดียว รายละเอียดตรวจ dependency นี้เป็นข้อเสนอทางเทคนิคใน EP-14 เพื่อรักษากฎประยุกต์ข้างต้น

### 12.1 ตัวอย่างขอบเขตผลกระทบ

| สิ่งที่แก้ | bucket ที่ต้องรีเซ็ต | สิ่งที่คงเดิม |
|------------|----------------------|---------------|
| แก้ภาพ A-ZH ซึ่งใช้เฉพาะบนเว็บ ZH | ZH ทั้ง input A/B และน้ำหนัก | TH/EN input และน้ำหนัก; ภาพภาษาอื่น; Performance ทั้งหมด |
| แก้ A-TH โดย A มี EN/ZH ครบและไม่ใช้ TH สำรองบนสองเว็บนั้น | TH ทั้ง A/B          | ZH/EN input และน้ำหนัก |
| แก้ A-TH โดย A ไม่มี EN และไม่มี ZH | TH, EN, ZH เพราะทั้งสามเว็บอ้างสื่อนี้ | Source อื่นและ Performance |
| แก้ A-TH โดย A มี ZH แต่ไม่มี EN | TH และ EN; ZH ใช้ภาพ ZH ของตน | ZH input และน้ำหนัก |
| แก้ B Video ชุดเดียวที่ทุกเว็บใช้ | TH, ZH, EN ทั้ง A/B ของ Source นั้น | Source อื่นและ Performance |

แม้แก้เฉพาะ A ของ bucket ที่กระทบ ต้องเริ่ม input B ของ bucket นั้นใหม่ด้วยเพื่อเริ่มช่วงเปรียบเทียบเดียวกัน ไม่ล้าง B เฉพาะบางอุปกรณ์เพราะใช้ไฟล์ร่วม

### 12.3 มีข้อมูล ZH ใหม่หลังแก้

สมมติก่อนรอบรายวันมี ZH ใหม่ A=12 Click/200 IMP และ B=2 Click/200 IMP โดย TH/EN ไม่มีข้อมูลใหม่เพิ่ม

| ข้อมูล / ขั้นคำนวณ | ผล  |
|--------------------|-----|
| input A ZH หลังรีเซ็ต | 12 / 200 → CTR 6% |
| input B ZH หลังรีเซ็ต | 2 / 200 → CTR 1% |
| RAW_P_A[ZH]        | 6 ÷ (6+1) × 100 = 85.714286% |
| น้ำหนัก ZH หลังจำกัดช่วงในรอบรายวัน | 70:30 |
| น้ำหนัก TH / EN เมื่อไม่มีข้อมูลใหม่ | TH 66.67:33.33 และ EN 50:50 |
| Performance ZH ที่ยังเก็บก่อนแก้และหลังแก้ | A=(10+12)/(1,000+200)=22/1,200; B=(50+2)/(1,000+200)=52/1,200 |

หากนำ Performance ZH มาคำนวณแทนจะได้ CTR ประมาณ 1.8333% และ 4.3333% → น้ำหนักดิบ A ประมาณ 29.7297% → จำกัดเป็น 30:70 ซึ่ง **ไม่ใช่** น้ำหนัก input หลังรีเซ็ตที่ต้องเป็น 70:30 ตัวอย่างนี้ใช้แยกข้อมูลสองหน้าที่ให้ชัด ไม่ใช่คำสั่งลบประวัติเก่า

ถ้าแก้หลายสื่อพร้อมกัน ใช้ผลรวมของ bucket ที่กระทบโดยไม่รีเซ็ตซ้ำเป็นหลายช่วงในเหตุการณ์เดียว เช่น A-ZH และ B Video กระทบครบสาม bucket ให้เริ่ม A/B ทั้งสามและ 50:50 ทั้งสาม ส่วน Source อื่นไม่เปลี่ยน

## EP-14 ข้อควรส่งต่อทีมพัฒนา ข้อจำกัด และรายการรอชี้ขาด

### 14.1 แนวทางข้อมูลและการควบคุม — ข้อเสนอทางเทคนิค

รายการต่อไปนี้เป็น **proposal** ไม่ใช่การอ้าง endpoint schema หรือพฤติกรรม production ที่ตรวจพบ

| เรื่อง | แนวทางที่เสนอ | กฎที่ต้องรักษา |
|--------|---------------|----------------|
| ข้อมูลเหตุการณ์ | อ้าง Source, variant A/B, web_language, media_language, รหัส/รุ่นสื่อ และอุปกรณ์ตามเหตุการณ์ที่แสดงจริง | bucketเว็บเลือกก่อนสื่อ;เหตุการณ์เดียวไม่ลงinputซ้ำ |
| input และน้ำหนัก | เก็บinputและจุดรีเซ็ต Source+web_language;น้ำหนักสามชุดรวมอุปกรณ์ | ไม่ใช้คู่ภาษา–อุปกรณ์จากTopกับไฟล์ร่วมInsert |
| ความสัมพันธ์สื่อกับbucket | ตรวจทุกทางเลือกที่อาจถูกเลือกว่าสื่อ/eligibilityก่อนและหลังเปลี่ยนถูกใช้บนเว็บภาษาใด ทั้งตรงและfallback ไม่ใช้เฉพาะผลrenderครั้งล่าสุด | รีเซ็ตเฉพาะbucketที่กระทบและทั้งA/B |
| ประวัติPerformance | เก็บประวัติและรุ่นสื่อเดิมต่อให้inputเริ่มใหม่ | ไม่ลบผลจริงและไม่เอาClickสื่อเก่าปนinputใหม่ |
| แก้สื่อชนรายวัน | ผูกผลคำนวณกับรุ่น/จุดรีเซ็ต และปฏิเสธผลที่เก่ากว่าการแก้ล่าสุด | ไม่ให้ค่าน้ำหนักเก่าเขียนทับ50:50ที่เพิ่งตั้ง |
| เกณฑ์Click/IMP | ใช้เกณฑ์เหตุการณ์ของระบบเดิมและยืนยันกับทีมที่ดูแล | ไม่สมมติว่าโหลดรายการเท่ากับIMPหรือเพิ่มเวลามองเห็นขึ้นเอง |
| ผลสุ่มกับการทดสอบ | ตรวจหน่วยCandidate จำนวนลำดับขั้น bucketที่ใช้ และสื่อที่เลือกได้;ใช้fixtureควบคุมผลเพื่อพิสูจน์ตัวอย่าง | ไม่ตัดสินว่าผิดจากผลสุ่มรอบสั้นไม่ตรงสัดส่วน |
